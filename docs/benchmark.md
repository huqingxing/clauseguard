# 压测报告：20 并发 / 5 分钟（Stage 14）

> 结论先说：**220 份合同零失败、单份 ¥0.013984、主端点 P50 25s / P95 30s / P99 33s**；
> 但真正要记住的是第三张表——**吞吐在 4 并发时就到顶（≈0.7 run/s），之后加并发只加等待，不加吞吐**。
> 这一条决定了「扩容该加 worker，还是该加机器」。

- 日期：2026-10-26
- 代码版本：Stage 14 提交（`git log` 中「Stage 14 可观测性与交付物」；压测在该版本上测得）
- 被测对象：Python 编排层 `POST /v1/runs`（`python-agent`，uvicorn **单 worker**）
- 压测工具：Locust 2.47.0，`deploy/locust/locustfile.py`

## 1. 口径（比数字重要）

| 项 | 定义 |
| --- | --- |
| 一次请求 | `POST /v1/runs` 发出 → SSE 流结束（收到 `run.completed` 或 `run.interrupt`） |
| 一次旅程 | 提交审查 → 遇审批断点 → `POST /v1/runs/{id}/resume` → 拿到 `run.completed`；记为 **2 个请求** |
| 失败 | HTTP 非 200 / 流里出现 `run.failed` / 流结束仍未收到 `run.completed` |
| 时延 | 墙钟：请求发出到响应体读完（含下载合同、切分、46 次模型调用、critic、回写） |
| 成本 | `run.completed.usage.cost_cny` 累加；单价 输入 ¥0.0008/1K、输出 ¥0.002/1K |
| 模型后端 | **mock**（`MODEL_BACKEND=mock`，每次调用固定 `asyncio.sleep(0.12s)`），不接供应商 |

## 2. 环境

| 项 | 值 |
| --- | --- |
| 机器 | 本机（AMD64，16 逻辑核，Windows），压测客户端与被测服务**同机** |
| Python | 3.12.10 / uvicorn 单进程（未开 `--workers`） |
| checkpoint | MemorySaver（`PG_DSN` 留空，不起 Postgres） |
| 输入合同 | `deploy/demo/demo-contract.docx`（14 条条款，含 2 条高风险，必然触发审批断点） |
| 规模 | 20 用户、spawn rate 4/s、持续 5 分钟、无思考时间 |

## 3. 主结果（分端点）

| 端点 | 请求 | 失败 | P50 | P95 | P99 | 均值 | 最大 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `POST /v1/runs`（提交审查） | 220 | 0 | **25.0s** | **30.0s** | **33.0s** | 24.9s | 33.3s |
| `POST /v1/runs/{id}/resume`（审批后恢复） | 220 | 0 | 0.27s | 4.3s | 8.3s | 1.14s | 8.3s |

- **旅程完成 220 / 启动 240，失败 0，错误率 0.00%**（差的 20 份是 5 分钟到点关停瞬间在途的旅程，不是失败）
- 墙钟 298.9s → 吞吐 **0.74 run/s ≈ 44 份/分钟**
- 累计请求 440（全程 2 个请求/旅程，与「演示合同必然中断」一致）

> 为什么必须分端点：混在一起算（Locust 的 Aggregated 行）得到 P50 **16.0s**——这个数既不代表
> 审查（25s）也不代表恢复（0.27s），只代表「两种量级混在一起的中间值」。报告里只用主端点。

## 4. 成本与 token

| 指标 | 总量 | 单份 |
| --- | --- | --- |
| 输入 token | 1,821,600 | 8,280 |
| 输出 token | 809,600 | 3,680 |
| 估算成本 | ¥3.0765 | **¥0.013984** |

单份 46 次模型调用、每次 180 in / 80 out（可由 token 反推：8280/180 = 3680/80 = 46）。
单份成本 ≈ 46 × 0.12s 的替身延迟上限 = 5.5s 串行，实测单跑 3.5s（见下节，6 专家分片并行摊掉了一部分）。

## 5. 并发拐点（本报告最重要的一张表）

| 并发 | 主端点 P50 | 观察到的吞吐 | 说明 |
| --- | --- | --- | --- |
| 1（`single_run.py` 串行 3 次） | **3.49s** | 0.29 run/s | 无争抢基线：3.83 / 3.46 / 3.49 |
| 4 | 6.1s | ≈0.50 run/s | 已经接近天花板 |
| 10 | 13.0s | ≈0.42–0.7 run/s | 短窗口（25s）未完全预热，量级参考 |
| 20 | 25.0s | **0.74 run/s** | 5 分钟正式跑 |

读法：

1. **P50 随并发线性上涨（3.5 → 6.1 → 13 → 25），吞吐却几乎不动**。这不是「模型慢」，替身的
   `asyncio.sleep(0.12)` 不占 CPU；是单进程内同步段（docx 解析/切分、渲染、序列化）与事件循环
   争用，把并发排队换成了延迟。
2. Little's law 复核：20 用户 ÷ 0.74 run/s ≈ 27s，实测 P50 25s，自洽。
3. **所以 20 并发不是一个「能扛」的结论，而是一个「已经排队」的结论**。要真提吞吐，扩容点是
   `uvicorn --workers N` 与多实例（每进程独立事件循环），不是提高 `concurrency_limit`
   （那是单 run 内的专家分片并发，只影响单份的内部时延）。
4. 审批往返（resume）P50 **0.27s**、占旅程总时延 **1% 量级**——审批断点的工程代价可以忽略，
   这正是 ADR-0004 敢把审批做进图里的底气。

## 6. 与 Stage 13 评测时延的关系（别把两个数放在一起比）

| 来源 | 口径 | 数字 |
| --- | --- | --- |
| `eval/out/report.md` | 单进程、串行跑 120 份、每份 ~4 条条款 | P95 4886ms |

对外只引用与当前语境一致的数：讲质量用评测报告，讲容量用本报告的分端点 P 值。

## 7. 复现

```bash
# 1. 起编排层（mock 后端；真实模型去掉 MODEL_BACKEND 即可）
make run-py MODEL_BACKEND=mock

# 2. 另一终端：20 并发 5 分钟（产出 eval/out/bench*.csv 与 bench-tokens.json）
make bench

# 3. 单并发基线（把「排队」从「业务本身」里剥出来）
python-agent/.venv/Scripts/python.exe deploy/locust/single_run.py --times 3

# 4. 拐点扫描（4 / 10 并发各 25 秒）
LOCUST_SUMMARY=eval/out/bench-u4.json python-agent/.venv/Scripts/python.exe -m locust \
  -f deploy/locust/locustfile.py --headless -u 4 -r 4 -t 25s --host http://127.0.0.1:8000 --only-summary
```

`eval/out/bench-tokens.json` 是机器可读版本（含 `by_endpoint`、`wall_clock_s`、`journey_s_total`）。

## 8. 已知局限（引用这些数字时必须一起说）

1. **mock 后端**：不含供应商真实时延、限流、重试与 429；真实模型下 P50 会由「模型延迟 × 分片轮次」主导。
2. **同机压测**：Locust 与被测服务抢同一批 CPU，客户端本身也在放大 P95。
3. **单 worker**：`uvicorn` 单进程是当前部署形态；多 worker 下的吞吐曲线本报告没有测。
4. **内存 checkpoint**：MemorySaver 比 Postgres 快，生产（PostgresSaver）会引入写盘开销。
5. **演示合同固定**：14 条条款、固定合同，未覆盖大合同（100+ 条）下的分片负载。
