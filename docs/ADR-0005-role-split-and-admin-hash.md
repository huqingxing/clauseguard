# ADR-0005: 按角色拆两端（提交者 / 审核者）、管理端走 hash 路由、用户端接口暂不鉴权

- 状态：已接受
- 日期：2026-10-27
- 相关：[ADR-0001 双栈分工](ADR-0001-architecture.md)、[ADR-0004 中断恢复](ADR-0004-interrupt-resume.md)

## 背景

基线（011579f）把「发起审查的人」和「拍板的人」放在同一套界面里：用户端 4 条路由含
`/reviews/:id/approve`，管理端是 2 屏手切 hash。三件事因此互相打架：

1. 审批链接谁都能打开——提交者打开的是审核者的页面；
2. 审核者反而没有入口——「我该批哪些」被外包给提交者把链接发过来；
3. 运维健康（谁探谁、依赖通不通）与评测看板（成本结构）和合同审查挤在同一个导航里，
   这些不是给签约方看的东西。

同时 `/api/v1/admin/**` 完全裸奔：拆入口只解决「看不见」，不解决「进不来」。

## 决策一：按角色拆，而不是按功能拆

- 用户端 = **提交者视角**：上传、发起审查、看结果、等审批。3 条路由。
- 管理端 = **审核者/内部视角**：运维健康、评测看板、待审批队列、审批详情。4 条路由。
- 审批归管理端，用户端不留任何审批入口（按钮、链接、隐藏入口都没有），
  旧地址 `/reviews/:id/approve` 落到 404 页并说明审批已迁走。

**为什么按角色而不是按功能**：功能只决定页面放哪儿，角色才决定「谁能看见、谁能拍板」。
按功能拆会把「审批」当成一个页面搬来搬去，搬完仍然谁都能打开；按角色拆时才看得出
「审批写入」这个动作本身需要受保护。拆完之后，「/api/v1/admin/** 要鉴权」才是一件
有对象的事——单页阶段没有角色概念时，鉴权是无对象的成本。**这也是 401/403 必须在
后端判定而不是前端藏起来的原因**：藏起来的入口只是让诚实的人点不到。

**代价**：跨端只能走绝对链接（`admin.html#/approvals/:id`），两端不共享 store——
管理端不装 pinia，审批页自己订阅事件流（事件从 seq 0 可回放，直开链接照样重建快照）。

## 决策二：管理端用 hash 路由（`createWebHashHistory`）

**为什么不是 history**：管理端是**独立 HTML 入口**（`admin.html`）。history 模式下
`#/approvals/<id>` 变成 `/admin/approvals/<id>`，服务端必须为每条子路由配 nginx
`try_files` 回退，否则刷新即 404；hash 模式下服务端永远只看到 `/admin`，深链接、
刷新、复制地址都不需要服务端配合。

**为什么不是继续手切 hash**（`watch` + `hashchange`）：审批页带 `:id` 参数后，手切撑不住
参数解析、浏览器前进/后退，标题也要靠一个缺 `immediate` 的 watch（首屏永远是默认标题）。
换成真 router 后，`afterEach` 写 `document.title` 连首次导航也覆盖，所以直开深链接的标题
就是对的——**这是选 router 的附带收益，不是额外工作量**。

**代价**：URL 里带 `#`；不能用 history 模式的 `scrollRestoration` 等能力（本端用不到）。

## 决策三：用户端接口暂不鉴权，只锁 `/api/v1/admin/**`

**为什么「暂不」而不是「不」**：

1. 要锁的是「泄露即损失」的那部分：双栈拓扑、成本结构、审批队列。用户端目前**没有
   用户主体**——没有用户表、没有注册、没有登录态，凭空造一套账号体系属于范围外的大改，
   且会同时改契约（`X-Operator` 这类字段的语义要从「客户端自称」变成「服务端认定」）。
2. `permitAll` 是**明确登记并写进 README 已知限制**的取舍，不是漏配；配套动作是
   `/api/v1/admin/**` 真上 `ADMIN` 角色、401/403 返回自己的 JSON（不是 Spring 默认 HTML）。
3. 已知缺口已登记，不是有意放行：`POST /api/v1/reviews/{id}/approve` 仍在 `permitAll` 下——
   知道 URL 就能绕过管理端页面直接批。`X-Operator` 现在取登录账号，比手填强，
   但仍是「客户端自称」。要真锁，得把它挪进受保护前缀或单独加规则。

**什么时候必须改**：对外上线前（README 已知限制第 13 条）。判据是「有没有外部用户」，
不是「有没有时间」。

## 备选与否决理由

| 方案 | 否决原因 |
| --- | --- |
| 单页 + 角色开关（同一套路由按角色隐藏） | 隐藏不等于隔离：管理端 URL 与文案仍留在用户端包里，且权限判断散落各组件，每加一屏就漏一处 |
| 管理端用 history 路由 + nginx `try_files` | 每条子路由都要服务端回退配置；hash 模式服务端只需认 `/admin`，少一处会漂移的配置 |
| 用户端也一起上 BASIC | 没有用户主体，凭空造账号体系超出本阶段范围；先锁住真正需要锁的，并把缺口写清楚 |
| 待审批做成「队列 + 认领 + 派发」 | 引入指派人、认领、并发保护三套语义；队列只解决「待办在哪儿」，不解决「谁来干」，后者留给下一阶段 |
| 审批队列单独建表 | 待审是 `review.status` 的一个取值，单独存表就要为「谁把它删掉」负责，漏同步即出现幽灵条目 |

## 后果

- 两端产物按入口切分：用户端可达 chunk 中 `grep "api/v1/admin|api/v1/eval|运维健康|评测看板|待审批"`
  **0 命中**；但「两个包毫无共享」不成立——Element Plus / Vue / vue-router / Pinia 合成一个
  vendor chunk，两个入口都引它（同一份框架没必要打两遍）。
- 前端登录卡不是安全边界，只是把凭证带给后端；任何 admin 请求 401 都清凭证退回登录卡。
- 旧审批地址不再静默回列表（会被读成「跳错页了」），改为 404 页说明审批已迁到管理端。
- 跨端跳转靠绝对链接，因此管理端的路由形态（hash）写进了用户端的链接里——这是两端之间
  唯一的硬耦合点，改管理端路由形态时必须同时改 `RunPanel` 与 404 页里的链接。
