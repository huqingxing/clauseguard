# RAG 检索实验台 · 阶段 7：把检索改进量化到业务指标

> 本文面向**不懂本项目**的人。读不懂的地方看「术语速查」。所有数字来自真模型在 30 份合同上的实跑，没有挑好看的数字。

## 0. 先说人话

ClauseGuard 是一个「合同审查」系统：把一份合同喂进去，AI 找出里面的法律风险并附上法条依据。
之前系统的「法条检索」是**假的**——它每次都返回几个写死的占位法条（编号 `sim-001` 这类），AI 引用的也是这些不存在的法条。
我们花了前几个阶段把检索换成**真的**：连上 PostgreSQL + pgvector，把《民法典》《公司法》等真实法条切成 2584 段、做了向量 embedding，能按语义搜出真实法条。

阶段 7 要回答一个问题：**把假检索换成真检索，审查质量到底变好了还是变差了？**

结论先摆出来（诚实版）：
- **引用可验证性**：假检索给的是假法条 ID，永远无法核对；真检索给的是真实法条（如《民法典》第 585 条），可以逐条核对。这一项**真检索严格胜出**。
- **风险召回率**（合同里真实存在的风险，AI 有没有找出来）：假检索 96.6%，真检索 **29.1%**。**真检索反而大幅下降了**。
- 这不是「检索变差了」，而是暴露了一个**架构设计缺陷**：旧系统无意中把那套固定检索池当成了「风险清单」塞给模型当提示，模型因此很全面；真检索是「按问题搜」，去掉了这个副作用。

| rerank | 检索出一批后，再用一个小模型对结果重新排序，理论上更准，但更慢更贵。 |

## 1. 问题定义

**为什么模拟检索不可接受？**

1. **引用无法核对**：mock 返回的 `sim-001` 这类 ID 不指向任何真实法条。系统声称「引用了法条」，但审计/法务拿到后无法验证，等于没有依据。这在真实业务里是不可接受的——审查结论的法律效力来自所引法条。
2. **评估指标失真**：`eval/` 里原有的评测框架跑的是 mock 后端，金标的 `gold_source_id` 也是 `src-vat` 这类 mock 池 ID。指标再好看，衡量的是「模型能不能对齐假 ID」，不是「审查质量」。
3. **检索能力零复用**：所有真实法律知识都没进系统，换合同类型就露馅。

所以阶段 6 把检索换成真 pgvector；阶段 7 要把「换真检索」这件事**量化成业务指标**，证明它到底有没有用。

## 2. 实验设计

**核心思路：控制变量。** 只有「检索返回什么」这一个变量在变，其余全部钉死，这样两组差异才能归因到检索。

| 变量 | 控制方式 |
| --- | --- |
| 大模型 | 固定 `qwen-plus`（阿里云百炼），两组用同一个模型实例 |
| 提示词 / 拓扑 / 合同 | 完全不变，复用生产 `build_expert_agent` |
| 唯一变量 | 检索工具：mock = 返回固定 22 条风险目录候选；live = 阶段 6 接好的 pgvector 真实检索 |
| 数据集 | `eval/dataset/` 前 30 份合同（金标 117 个风险标注） |

**指标与判定口径：**

- **风险召回率**：金标 `(合同, 条款, 风险类型)` 三件套，被 AI 终态结论命中即算 TP。与「引用是 mock 还是真」无关——它衡量的是「AI 有没有发现这个风险」。
- **引用准确率**：金标 ID 体系（mock 池）与真检索 ID 体系（`civil_code:...`）不可比，无法自动比对。改用**人工抽检 30 条**：逐条读「结论 + 引用法条原文 + 合同上下文」，判定 `support`（直接支撑）/ `partial`（主题相关但只支撑一部分）/ `not_support`（法律性质不符或完全偏题）。

**为什么这样设计：** 风险召回率回答「审查变全面了吗」，引用准确率回答「引用的法条靠不靠谱」，两个维度合起来才能说清「检索变好 → 审查变好」是否成立。

## 4. rerank 取舍

检索实验台（阶段 5）的结论：

- 最优参数组合是 `S5_context | E1`（上下文切分 + 1024 维 embedding），`recall@5 = 0.6146`。
- **关键事实**：所有参数档位的 95% 置信区间互相重叠，即「差异在统计上不显著」。阶段 4/5 报告明确写了这一点。
- rerank（`gte-rerank-v2`，真实端点实测）：单次 20 个候选约 **744.89ms、2725 tokens**，相对检索 P50（13.27ms）约 **56 倍**延迟与可观成本。

**决策：当前不部署 rerank。** 理由——在检索实验台里 rerank 没有证明出统计显著的收益，却带来 56 倍的延迟/成本；且生产 `retrieval.yaml` 的 `use_rerank` 已置 `false`，接了也会 503。rerank 是一个「待验证、暂不启用」的能力，不是被遗忘的优化。

## 5. 对业务指标的影响（诚实结论）

**改造后风险召回率从 0.9658 掉到 0.2906，下降 67.5 个百分点。**

这不是「真检索检索得差」——真检索在引用真实性上更好。根因是**架构把检索池误用成了风险清单**：

- mock 检索工具每次返回**固定的 22 条风险目录候选**，与问题无关。这等于把 19 类风险的「菜单」持续喂给模型，模型因此很全面（召回高）。
- live 检索是**按 query 语义搜真实法条**，返回的是具体、窄的法律条文，不再提供那张「风险菜单」。模型失去了隐式提示，**产出的结论数从 201 骤降到 70**，丢失的 79 个金标遍布所有风险类型。

**这说明：在当前架构下，「检索变准」≠「审查变好」。** 检索当前同时承担两个角色——（1）给结论找法条依据；（2）无意中给模型当风险覆盖清单。我们修好了角色（1），但角色（2）的副作用被去掉后，暴露了**底座提示词本身并不独立覆盖全部 19 类风险**。

**修复方向（不在本阶段动手，列为遗留）：** 把「风险覆盖」和「引用证据」解耦——在提示词里显式枚举 19 类风险让模型逐项排查，检索只负责为命中的风险找真实法条。这样真检索才能在不丢召回的前提下，把引用从假 ID 换成真法条。

## 7. 结论

1. **引用真实性**：真检索把假 ID（`sim-001`）换成真实法条（`civil_code:...`），引用第一次变得可核对——这是 mock 永远给不了的，业务价值明确。
2. **风险召回**：真检索在「当前架构」下把召回从 96.6% 拉低到 29.1%。**这是架构缺陷暴露，不是检索变笨**：旧 mock 池无意中当风险清单用，真检索去掉了这个副作用。
3. **引用精度**：抽检 30 条，严格支撑 46.7%、宽松 90%、3 条硬错（法律性质不符/偏题）。真检索「找得到相关法条，但还不会挑最对的」。
4. **rerank**：无统计显著收益、成本 56 倍，**暂不部署**。
5. **一句话**：真实检索是必要的地基，但它单独上线会拉低召回；必须先做「风险覆盖与引用证据解耦」才能两全。

## 8. 局限

- **样本量小**：仅 30 份合同、117 个金标风险标注。置信区间宽，单合同波动大；严格准确率 ±18 个百分点量级的误差不可避免。
- **标注者单一**：引用抽检由一人（仓库维护者）完成，未做多人独立标注与一致性检验（Kappa 等）。判定带主观性，尤其 `partial` 边界。
- **语料规模有限**：法条库 2584 段，覆盖《民法典》《公司法》《广告法》《民事诉讼法》等，但非全量法规；某些专业领域（如跨境 PIPL、出口管制）条文密度不足，直接反映在第 13、26 条偏题。
- **模型依赖**：实验固定 `qwen-plus`，结论未必迁移到其他模型；且大模型本身有随机性，两次跑会有波动。
- **召回口径**：风险召回衡量「有没有发现风险条款」，不直接衡量「结论法律正确性」。召回高不等于结论对，只是漏检少。
- **未上线验证**：以上在离线评测跑通，未接入生产流量；真实用户合同分布可能与评测集不同。
